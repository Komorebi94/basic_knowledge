# 任务、微任务与渲染时机

> 设计样稿 · K02-01 · 核心 · 预计 10 分钟 · 核验 2026-09-30  
> 建议 slug：event-loop；前置 K01-02；关联练习 E03、E10。

## 你将解决什么问题

点击“开始计算”后，页面明明先把提示改成了“正在计算”，用户却要等计算结束才能看见变化。你需要区分：代码改了状态、DOM 已更新、屏幕已绘制，并不是同一件事。

## 核心结论

浏览器把任务、微任务与渲染机会放在不同的调度环节；在微任务检查点会处理队列里后续加入的微任务。一次任务结束不等于一定绘制一帧，持续产生微任务也可能延迟页面响应。[HTML 标准](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops)。

JavaScript 语言执行需要宿主配合，浏览器和 Node 的调度不能混成同一套固定口诀。[MDN 执行模型](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model)。

## 按时间线理解

考虑一个原创的简化场景：同一次按钮回调里先记录 A，安排一个已兑现 Promise 的回调记录 C，安排一个零延时定时器记录 D，最后同步记录 B。不考虑其他代码与取消操作。

| 顺序 | 发生的事 | 观察结果 |
| --- | --- | --- |
| 1 | 当前按钮回调开始，执行同步语句 | A |
| 2 | 登记后续回调，继续当前同步代码 | B |
| 3 | 到相应微任务检查点，执行 Promise 回调 | C |
| 4 | 定时器任务在符合调度条件后得到执行 | D |

这里用于解释顺序，不保证 D 恰好 0 毫秒执行，也不保证 C 与 D 之间必定出现一次屏幕绘制。未来正文代码示例必须在声明浏览器中实际验证，并附运行步骤。

## 工程应用

要修复开头的交互，先做性能记录，确认主要时间花在同步计算还是布局/绘制。若是大块纯计算，考虑拆成可让出主线程的工作片段，或者把适合转移的工作交给 Worker。若问题是反复读写布局数据，先减少布局往返。

这里的选择要根据任务规模与数据传输成本决定。把所有计算都移进 Worker 并非免费优化；把计算包进 Promise 也没有自动转移线程。

## 两个常见误区

**“异步就是不会卡页面。”** 回调里的大量同步工作仍可能占用主线程。应检查工作实际在哪个执行环境运行，而不是只看函数是否标成 async。

**“await 一下页面就会绘制。”** 等待一个已兑现结果不构成“已绘制”的保证。应明确需要的是逻辑顺序、下一帧回调还是把工作让出主线程。

## 取舍与边界

这里讨论浏览器的常见调度理解，不承诺跨任务来源的全部执行顺序。不要用特定机器一次控制台输出推导所有环境。若要解释某个框架的更新时机，还需要查看该框架自己的调度与刷新规则。
